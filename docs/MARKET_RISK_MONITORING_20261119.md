No DNS, production schema, provider plan, customer email, wallet permission or transaction is changed by development.

It loads only when expanded and visible, and unmounts on close, hidden tab or offline state. Pair/theme changes replace the sole frame. Reload is bounded to once per 15 seconds. Provider-managed reconnects/history are internal to the official embed; Rivexis does not claim to monitor its socket or independently certify its freshness. Attribution, source identity and limitations remain visible. No widget prices/messages/candles are extracted, cached, exported, evaluated or used as a production feed.

The official loader runs in a fixed-content `data:` iframe with an opaque origin. `allow-same-origin` permits its nested TradingView frame to use its own origin; the outer `data:` document still cannot access Rivexis cookies, storage or DOM. **Do not change this to `srcDoc`, a blob URL or an application-hosted page while retaining scripts and same-origin permissions.** No untrusted symbol, HTML or URL enters the document. The app installs no third-party script in its own document. Browser testing reproduced and repaired the official nested widget's cookie failure when all descendants were forced into an opaque origin.

Existing Chainlink reference observations remain separate, now with their histories collapsed by default and feed/raw-unit evidence available on demand. These are sparse oracle observations, not exchange candles. Network/base-fee charts remain in Overview, Networks and GasGuard; transaction-specific simulation still obtains independent fee estimates. Existing position histories and hypothetical risk/frontier diagrams retain their financial models and accessible tables. No new dashboard page, ticker, fabricated volume or synthetic price history is added. Advanced Charts is not used: no access/licence is assumed. Lightweight Charts is unnecessary for this small provider-owned context display; existing specialized risk diagrams are retained.

Market observation retention now rejects backwards heads and conflicting oracle rounds, bounds each series to 96 observations, and discards both fee and quote histories after detected reorganizations/overlap conflicts. Ownership changes remount the market session. Failed manual attempts also observe the 15-second bound; retry backoff survives visibility/navigation changes. Existing per-minute visible-tab polling, cancellation and five-minute missing-history retry remain. No credential moves to the browser. Public reference data is not mixed into protocol liquidation calculations.

## Monitoring contract and durable execution

`GET/PATCH /api/v1/defi/monitor` follows existing verified-session, same-origin/CSRF, body limits and no-store protections. The server supplies `auth.user.id`; caller-selected owners, recipients, RPC hosts, deployments, prices and chains are rejected. The new owner-private scope matches personal DeFi reports; it does not enroll or expose shared workspace/organization monitors. The legacy generic monitors/alerts remain separate.

The API flag `RIVEXIS_DEFI_MONITOR_ENABLED` defaults off. A disabled GET reports `INACTIVE` without touching new storage; a disabled mutation fails closed. With the flag on, availability also requires the worker's recent persisted heartbeat. Save acknowledgement must include the matching persisted rule. Lost/malformed/mismatched responses never produce a saved notice or automatic write retry. Settings links to the existing Monitoring & Reports surface for optional preferences and delivery evidence.

The additive migration creates three RLS tables: owner rules, durable events/outbox and private runtime state. Authenticated clients can SELECT their own rules/events only. They cannot write rules/evidence, read runtime, choose an owner or execute either RPC. Service-only, invoker RPCs retain explicit grants and fixed search paths; no new public security-definer surface is added. Existing tables and migrations are not rewritten.

The short `rivexis-defi-monitor` Edge invocation is triggered by supported Supabase Cron + pg_net, with the worker token held in Vault/runtime secrets. It performs at most one evaluation and one delivery attempt, with a 55-second total abort and an 8-second send timeout. No browser timer, `waitUntil` or long-running Edge loop is sold as durable protection. The migration does not install a job. The separate reviewed activation recipe is `infrastructure/supabase/defi-monitor-cron.sql`.

Rules are bounded to one per owner and three enabled globally. Normal evaluation is every 30 minutes, sharing the unchanged 300/day global and four/wallet/minute quota. Missing quota acknowledgement prevents the snapshot. Failures back off from 30 minutes to four hours. Leases last 90 seconds; duplicate/restarted jobs cannot commit a stale token/version. A configuration/consent change fences a claimed job, and identical saves are idempotent. No missed-period history is invented after a restart.

Evaluation uses the existing pinned, reconciled protocol snapshot and validators, then recomputes the minimum health across **independent** supported positions using integer mathematics. Current coverage remains normal-mode Ethereum Aave V3 with validated WETH/USDC/USDT/WBTC adapters, and the pinned Morpho WBTC/USDC 86% LLTV market. eMode, isolation, other chains/markets and changed unvalidated contracts fail closed. No market quote or scenario shock enters current risk. Thresholds retain 18 decimals; alert at or below the chosen threshold (1–3), recovery at or above a threshold at least 0.05 higher (up to 4). Debt-free health is null, never an invented finite number. Unavailable evidence preserves the previous condition and last successful timestamp. A changed previous block hash invalidates evidence/events and cannot create a recovery claim.

No warning before liquidation is guaranteed. Thirty-minute checks can miss rapid changes, and shared quotas can interrupt coverage. UI distinguishes the last attempt, last successful evaluation, retained condition, worker heartbeat and email availability; stale/missing heartbeat cannot present current worker availability. The original five visible-browser checks remain independently labeled and available.

## Notifications and delivery semantics

Email opt-in is false by default. No existing user is enrolled. The verified Auth email is looked up server-side; no alternate recipient is accepted. Detection and sending are separated by the transactionally persisted outbox. A rule/episode/kind uniqueness constraint prevents duplicate logical alerts. One-hour same-kind delivery cooldown, recovery hysteresis, condition/episode checks, cancellation of superseded pending events, one-hour event expiry and a ten-event daily send cap limit noisy or obsolete messages. Confirmed 429 rejection alone can retry, at five minutes, at most three attempts; no unknown send is blindly replayed.

States are `QUEUED`, `SENDING`, `ACCEPTED`, `DELIVERED`, `BOUNCED`, `FAILED`, `UNKNOWN`, `EXPIRED`, `CANCELLED`, `INVALIDATED`. A 2xx needs a message ID to establish **acceptance only**. Duplicate-without-receipt, timeout, transport error, malformed receipt or 5xx means UNKNOWN. A crash/lost mark leaves SENDING, which durable recovery changes to UNKNOWN. Provider tags retain the event reference for reconciliation. Delivered/bounced requires a matching receipt through the service-only ingestion RPC. **No public provider webhook is registered or enabled in this candidate**; automated receipt ingestion and real inbox acceptance remain activation blockers. Accepted events cannot be described as delivered.

Terminal event records expire after 90 days via once-daily worker cleanup. UNKNOWN/SENDING records are retained for operator reconciliation; monitor rules persist until owner/account changes or approved removal. Listing is capped at 20 events. No full financial snapshot, wallet balance or auth material enters email. The account export remains its existing profile/report scope; monitoring records are a separate owner-private view.

`infrastructure/brevo/defi-risk-update.html` and its sample JSON prepare one branded transactional template with safe defaults, a fixed authenticated Rivexis link and no contact-attribute dependencies. It is **offline preparation**, not a created Brevo template. Account/current-guide reads returned connector internal errors/timeouts. The installed Brevo writing/checking guides' offline workflow was followed; the HTML was checked by hand, not automatically validated or rendered by Brevo. Sender, company address placeholder, account capacity and domain status still need confirmation. Brevo preview with full, empty and missing-optional params must precede activation. No named test recipient was authorized; no test or customer send occurred.

Authentication remains on the existing Supabase Auth → Brevo SMTP integration. The new worker uses a separately gated transactional template/API path and cannot edit auth templates/SMTP. Its ten/day cap is incremental; total account capacity must include auth and legacy dispatch usage before activation. Do not claim a guaranteed auth reserve based only on the cap.

## Validation, approval and rollback

Local validation uses synthetic fixtures and retained dated protocol reference files, not customer accounts. Node tests cover threshold rounding, supported Aave/Morpho evidence, stale/future/invalid inputs, market/oracle separation, outbox uncertainty and bounded operations. The actual migration/RPCs execute in isolated PostgreSQL via PGlite, including RLS under ordinary authenticated/anon roles, service-only RPC grants, duplicate leases, consent fencing, idempotent saves, outbox lifecycle and reorganizations. CI also runs the SQL in a disposable PostgreSQL 17 database, separate from the existing legacy migration gate. Deno checks share the existing frozen import lock. Types, AST, Next and compiled-Worker builds are required. New browser fixtures cover inactive/stale monitoring, explicit opt-in, unknown saves, embed isolation/cleanup and both themes at mobile/desktop dimensions. Local pinned Playwright launch initially failed because its browser binary is absent; manual visual/functional checks use only the bundled Browser plugin, as requested. Do not equate prepared CI cases with passing CI until the exact head finishes.

Browser evidence compares baseline and candidate in local synthetic-account previews, with genuine **public** market/RPC observations separately identified. No authenticated financial production acceptance or real email delivery is claimed. Screenshots belong to the private task deliverables rather than a public redistribution of provider market data.

Activation requires separate specific approval, in this order: (1) protected merge/frontend release, which triggers existing main Builds; (2) additive production migration after an appropriate recovery point and disposable Postgres gate; (3) reviewed API and monitor function deployment/readback, approved server RPC configuration, token/Vault setup and the single named Cron job; (4) Brevo account/sender/address confirmation, inactive template creation and server preview, approved named test recipient plus acceptance/inbox/receipt verification; (5) explicit customer-email activation. Keep both monitoring flags false until their respective gates pass. Do not change DNS, install a paid plan, migrate customer data or request secrets in chat.

Rollback: first set `RIVEXIS_DEFI_MONITOR_EMAIL_ENABLED=false`, then disable evaluator and unschedule **only** `rivexis-defi-monitor-v1`. Preserve events, UNKNOWN outcomes, users and existing legacy jobs. Read persisted/runtime state to confirm inactivity. Leave the additive RLS tables in place for reconciliation; no automatic down migration or destructive restore. Restore the previously accepted API bundle if needed, and roll back the frontend only through the existing Worker version procedure in `DEPLOYMENT.md`. Recheck current accepted versions rather than treating old checkpoint IDs as current. Do not restore the database or change ingress to repair a UI/provider failure.
