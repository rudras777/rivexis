## Cross-engine contract rules

For newly executed live runs, the dispatcher enforces a canonical current engine version for each engine. Evidence records inside the run inherit that parent engine version while preserving a more specific shared/provider calculation version when one exists. This avoids a result claiming one methodology generation while its evidence claims an obsolete/default parent engine generation.

Provider consensus is derived from evidence actually present in the result: zero provider evidence cannot claim `SINGLE_SOURCE`; one provider is `SINGLE_SOURCE`; multiple providers are `MULTI_SOURCE`; unresolved provider conflicts are `CONFLICTING`. `USER_INPUT_ONLY` is preserved only for intentionally modeled results with no provider evidence.

Unresolved provider conflicts are also first-class analysis state. A fresh live result carrying `SourceConflict` records is promoted from ordinary `COMPLETED`/`PARTIAL` to `CONFLICTING_DATA`; `STALE_DATA` and terminal unavailable/failure states are preserved when they are the stronger primary gate.

The normalization is intentionally limited to **new live dispatches**. Historical persisted analyses are not rewritten because their stored versions are part of the audit record.

For F3, an explicit protocol-adapter request is a trust-boundary instruction. If that adapter path does not return an authoritative position, Rivexis does not silently substitute the generic modeled-oracle conclusion. It returns an explicit unavailable/insufficient state with zero confidence and UNKNOWN severity. The generic modeled path remains available only when the caller does not require an authoritative adapter result.

For B1, the canonical transaction-effects summary is a derived view of evidence already present in the result. It does not create provider facts or infer token/NFT transfers from call traces. Missing trace/state-diff coverage and absent event/log normalization are represented as limitations/coverage flags so downstream consumers can distinguish observed effects from unavailable effects.

For F1, direct ERC-20 balance reads are intentionally opt-in and metadata-constrained. Rivexis calls the declared contract's `balanceOf(address)` through the selected chain RPC and records the raw balance as evidence, but it does not infer token identity, decimals, symbol or market mapping from an arbitrary address. Duplicate rows sharing the same market asset ID are aggregated before concentration scoring.

For B5, the caller's route request is the trust-boundary contract. LI.FI quote fields are checked against that request before risk scoring. A route with mismatched source/destination chain, token, amount or addresses, a changed quoted slippage, a malformed expected/minimum amount, or a minimum amount larger than the expected amount is retained as evidence but cannot become an ordinary scored route. It is returned as `CONFLICTING_DATA` with UNKNOWN severity so downstream decisioning fails closed. A quote that matches its request is still only aggregator evidence and remains `PARTIAL` until independent bridge/security/liquidity evidence exists.

For B2, malformed target/sender addresses and transaction hashes are rejected before provider calls. When a transaction hash resolves, its sender/destination are revalidated before bytecode lookup or external security scanning. This prevents malformed caller/provider data from being mislabeled as an RPC/security-provider outage and prevents invalid address strings from crossing the external-provider trust boundary.

For B3, `previous_snapshot` is a change-detection trust boundary rather than arbitrary comparison input. Fresh dispatch rejects non-object snapshots, snapshots missing entity/chain identity, snapshots for a different entity/network, and mismatched token/oracle dependencies when both current and prior dependency identities are available. No provider call or delta scoring is allowed to turn unrelated state into withdrawal, bytecode, supply or oracle-change signals.

For F2, a usable provider record is required before scoring. Non-object or identityless records and non-finite/negative core TVL are rejected rather than converted into plausible fundamentals. When the TVL history contains a credible provider timestamp, that timestamp—not HTTP retrieval time—drives freshness. Missing/corrupt observation time stays `UNKNOWN`; stale/expired observations and an explicit provider `latestFetchIsOk=false` state gate the analysis as `STALE_DATA` so downstream decisioning cannot treat degraded fundamentals as ordinary partial evidence.

For F4, a selector is a strategy-identity boundary. An exact `pool_id` must resolve uniquely; a broader protocol/project + asset/symbol + chain selector is accepted only when it resolves to exactly one current DefiLlama pool. Multiple candidates are returned as an explicit insufficient-selection state rather than silently selecting the largest TVL. APY and TVL are core scoring inputs and must be finite (with TVL non-negative); malformed values do not become zeros. Stale or expired provider timestamps are a first-class `STALE_DATA` gate, while materially future timestamps are not treated as current evidence.

For F5, treasury inputs are decision-model inputs and must be validated before scoring. Negative or non-finite weights/quantities, non-positive supplied capital, out-of-range policy/shock percentages and non-boolean `stablecoin` flags fail closed rather than being normalized into plausible-looking allocation metrics. When weights are derived from quantities, every allocation must have a usable market mapping and positive current price; Rivexis does not silently assign an unpriced allocation zero exposure. Stale or expired market timestamps are a first-class `STALE_DATA` gate.

## External gates that remain non-code blockers

- Arkham remains license/terms-gated.
- Hypernative native screening remains customer-schema/contract gated where the exact authenticated request contract is not public/approved.
- Tenderly, Blockaid, Nansen, explorer and RPC behavior depends on deployment configuration and valid credentials/entitlements.
- Absence of those integrations must remain explicit provider-unavailable/partial/UNKNOWN-compatible evidence, not synthetic success.

## Remaining Milestone F work

The repository-level cross-engine provenance/version/consensus/conflict-status contract, explicit F3 adapter trust boundary, deterministic B1 transaction-effects summary, B2 input trust-boundary validation, B3 prior-snapshot identity validation, explicit F1 ERC-20 direct-balance path, B5 quote request/response integrity boundary, F2 provider-payload/freshness integrity, F4 selector/freshness integrity and F5 treasury-input/freshness integrity are covered. Remaining engine-depth work includes B1 canonical event/log asset-change normalization, deeper B2/B3 external threat/security evidence where approved, F1 automatic/indexed token discovery plus NFT/DeFi positions where an approved evidence source exists, independent B5 bridge/security/liquidity evidence, and the remaining B4 evidence-depth gaps plus F2/F4/F5 dependency/liquidity/counterparty depth. Keep credential/licensing/customer-contract gaps explicit and add per-engine regression evidence before advancing to monitoring/investigation/report completion.
